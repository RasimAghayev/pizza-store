# AWS Deployment

> Status: Phase 8 (Issue #160). AWS is the primary/detailed cloud provider per
> [ADR 0007](../adr/0007-deployment-target-priority.md) — Amazon MQ is the only one of the
> three providers with a native managed broker matching this project's actual messaging
> choice (RabbitMQ, ADR 0001). The skeleton in
> [`infrastructure/terraform/aws/`](../../infrastructure/terraform/aws/) is **validated-only**:
> `terraform validate`/`fmt -check` pass clean against the public provider registry, no
> backend is configured, and no AWS credential, account, or real resource exists anywhere in
> this repository or was ever created (master prompt §8/§18).

## Architecture

| Compose/Swarm service | Managed-AWS equivalent | Notes |
| --- | --- | --- |
| `nginx` (edge) | Application Load Balancer + ACM certificate | "Nginx as the edge" is a Compose/Swarm/Kubernetes-specific shape; a managed ALB with an ACM-issued certificate replaces both the reverse-proxy and TLS-termination roles. The `/api/*` path-based routing rule in `alb.tf` mirrors `infrastructure/nginx/conf.d/default.conf`'s location-block split. |
| `backend` / `frontend` | ECS Fargate services behind the ALB | Serverless containers; same pre-built-image constraint as Swarm (no `build:` support) and the same 2-replica rolling-update intent validated in Issue #158, here performed by ECS's own native deployment configuration. |
| `postgres` | RDS for PostgreSQL | `manage_master_user_password = true` — AWS generates/rotates the master password in Secrets Manager; Terraform never sees it. |
| `mongodb` | Amazon DocumentDB | **Not full parity** — see Compatibility caveats below. |
| `redis` | ElastiCache for Valkey | **Engine substitution, not Redis itself** — see Compatibility caveats below. |
| `rabbitmq` | Amazon MQ (RabbitMQ engine) | The deciding factor for AWS as primary provider (ADR 0007) — same engine, managed. |
| `infrastructure/compose/secrets/*.txt` | AWS Secrets Manager | Every credential (`infrastructure/terraform/aws/secrets.tf`) — RDS/DocumentDB manage their own secret natively; Amazon MQ/ElastiCache auth tokens/Django secret key/JWT signing key are generated by Terraform (`random`/`tls` providers) and stored as Secrets Manager secrets, never as literals. |
| `edge-net` / `data-net` / `monitoring-net` (Issue #158) | VPC public/private subnets + per-tier security groups | Public subnets hold only the ALB and NAT gateway; private subnets hold ECS tasks and every data store. Each data-store security group accepts traffic only from the ECS security group, never from the internet or from each other — the same isolation shape proven on Swarm's overlay networks. |

## Compatibility caveats (real gaps, not claimed parity)

- **DocumentDB is MongoDB *wire-protocol*-compatible, not the same server code.** The
  Compose stack runs `mongo:7`; DocumentDB offers no 7.x-compatible track at all — only 3.6,
  4.0, 5.0, and 8.0 (there is no 6.x or 7.x track to map onto). This skeleton defaults to the
  5.0 track (`documentdb_engine_version` in `variables.tf`) as the better-established option.
  Before any real migration, every aggregation operator, index type, and transaction pattern
  this project's backend actually issues against MongoDB would need to be checked against
  DocumentDB's [supported-operations list](https://docs.aws.amazon.com/documentdb/latest/developerguide/mongo-apis.html) —
  this is not assumed away here.
- **ElastiCache defaults to Valkey, not Redis OSS.** AWS recommends Valkey (the
  Linux-Foundation-governed fork) over Redis OSS for every new ElastiCache deployment — lower
  cost, and every new ElastiCache feature lands on Valkey first. Valkey is
  command/wire-compatible with the Redis OSS commands this project actually uses, but it is a
  different, independently maintained codebase, not upstream Redis. `elasticache_engine` in
  `variables.tf` can be switched back to `"redis"` if a real divergence is ever found.

## Cost comparison

Figures below are **illustrative single-point estimates from public AWS pricing pages as of
November 2026**, for this project's documented synthetic-dataset scale (master prompt §10: 10
branches, 20,000+ customers, 100,000+ historical orders) — not a quote, not validated against
a real AWS Pricing Calculator run, and no account was ever created to check them. Verify
current pricing before any real commitment.

| Component | Sizing (this skeleton's defaults) | ~Monthly estimate (us-east-1, on-demand) |
| --- | --- | --- |
| ECS Fargate (`backend` + `frontend`, 2 tasks each, 0.25 vCPU/0.5 GB) | 4 tasks × $0.04048/vCPU-hr + $0.004445/GB-hr | ~$36 |
| Application Load Balancer | 1 ALB, base hourly charge | ~$16 + usage-based LCU charges |
| NAT Gateway | 1 gateway (single-AZ default, see `vpc.tf`) | ~$33 + $0.045/GB processed |
| RDS PostgreSQL | `db.t4g.micro`, single-AZ | ~$12 (compute only; storage/backup billed separately) |
| DocumentDB | `db.t4g.medium`, 1 instance (non-prod default) | ~$55–70 (estimate; DocumentDB has no public per-vCPU rate as granular as RDS's) |
| ElastiCache (Valkey) | `cache.t4g.micro`, 1 node (non-prod default) | ~$12 |
| Amazon MQ (RabbitMQ) | `mq.m7g.large`, `SINGLE_INSTANCE` (non-prod default) | ~$200 (sourced: $0.2734/hr) |
| Secrets Manager | 6 secrets (`secrets.tf`) | ~$2.40 ($0.40/secret/month) + API-call charges |
| **Total (non-prod sizing)** | | **~$365–385/month**, dominated by Amazon MQ and DocumentDB |

`prod` environment sizing (`var.environment == "prod"`) doubles RDS to Multi-AZ, DocumentDB to
2 instances, ElastiCache to 2 nodes with automatic failover, and would reasonably move Amazon
MQ to `CLUSTER_MULTI_AZ` — roughly 1.7–2x the table above, still dominated by Amazon MQ.
Compare against [`docs/deployment/swarm.md`](../deployment/swarm.md)'s and the VPS deployment
doc's near-zero marginal cost on already-owned/rented compute — the managed-AWS path trades
that for operational effort (patching, HA, failover) AWS now owns instead of this project.

## Security comparison

| Concern | Compose/Swarm/Kubernetes | AWS |
| --- | --- | --- |
| Credential storage | File-based secrets (`infrastructure/compose/secrets/*.txt`, gitignored) / Swarm-native `secrets:` objects | AWS Secrets Manager, with RDS/DocumentDB's master password never passing through Terraform at all (`manage_master_user_password = true`) |
| Network isolation | Bridge networks (Compose) / overlay networks (Swarm) — proven via a real DNS-resolution failure in Issue #158's validation | VPC public/private subnet split + per-tier security groups, same deny-by-default shape, enforced by AWS's network layer rather than Docker's |
| Identity/access | OS-level file permissions on secret files; no fine-grained per-service AWS-style IAM | IAM roles per ECS task (execution role scoped to exactly the Secrets Manager ARNs it needs — `ecs.tf`'s `aws_iam_role_policy.ecs_task_execution_secrets`), least-privilege and auditable via CloudTrail |
| Transport encryption | Plaintext between containers on an isolated network (acceptable within a single trusted host/cluster) | `transit_encryption_enabled = true` on ElastiCache, TLS-only Amazon MQ listener, ACM-issued TLS at the ALB — encrypted in transit even though AWS's own network backbone is also isolated |
| Audit trail | Container/application logs only | CloudTrail (API-level audit of every resource change) in addition to CloudWatch Logs |

## Backup comparison

| | Compose/Swarm (this project's own scripts) | AWS |
| --- | --- | --- |
| Mechanism | `scripts/backup-postgres.sh` / `backup-mongodb.sh`, `gpg`-encrypted, see [`docs/runbooks/backup-restore.md`](../runbooks/backup-restore.md) | RDS/DocumentDB automated snapshots (continuous, point-in-time restore within the retention window) |
| Retention | Whatever the script/cron schedule and local-disk retention policy define | `backup_retention_period = 7` days (both RDS and DocumentDB, `rds.tf`/`documentdb.tf`) — a Terraform-managed, enforced setting rather than a script's own bookkeeping |
| Encryption | `gpg` at the application layer, independent of the storage layer | `storage_encrypted = true` at the storage layer (both RDS and DocumentDB), in addition to any application-layer encryption |
| Restore mechanism | Manual `gpg`-decrypt + `pg_restore`/`mongorestore`, tested per the runbook | Point-in-time restore or snapshot restore via the AWS API/console, no manual decrypt step |
| Operational ownership | This project owns the script, the schedule, and the failure mode if a backup silently stops running | AWS owns the automated-snapshot mechanism; this project only owns the retention/encryption *settings*, not the backup execution itself |

## Scaling comparison

| | Kubernetes HPA (Issue #159, sibling Task) | ECS Fargate (this Task) |
| --- | --- | --- |
| Trigger | CPU/memory (or custom metrics) crossing a threshold, evaluated by the HPA controller | CloudWatch alarms driving an Application Auto Scaling policy attached to the ECS service (not yet wired in this skeleton — `ecs_desired_count` is currently a static variable, not an autoscaling target) |
| Scale unit | Pod replicas within a Deployment | ECS task count within a service |
| Underlying compute | Must already exist (cluster nodes) — Kubernetes schedules onto pre-provisioned capacity | Fargate provisions compute per-task on demand — no node capacity to pre-provision or run idle |
| Stateful services | Not horizontally scaled in either model (see Issue #158's Database setup section for the Swarm-side reasoning); RDS/DocumentDB/ElastiCache scale vertically (bigger instance class) or via read replicas, not by adding arbitrary replicas | Same constraint — `aws_db_instance`/`aws_docdb_cluster`/`aws_elasticache_replication_group` scale by instance class or read-replica count, not by `desired_count` |

account:

```text
$ terraform init -backend=false -input=false

- Installing hashicorp/aws v6.74.0...
- Installing hashicorp/random v3.9.1...
- Installing hashicorp/tls v4.4.2...
Terraform has been successfully initialized!

$ terraform validate
Success! The configuration is valid.

$ terraform fmt -check -diff
(no output, exit 0 -- already canonically formatted)
```

No `terraform plan` or `terraform apply` was run against any real account — doing so would
require real AWS credentials, which this Task does not create or configure anywhere.
