# Contributing

## Principle

Infrastructure first, business second. See [README.md](README.md) and `docs/architecture/`.

## Workflow

All work is managed through GitHub Issues. Every change is tied to an Issue.

1. Pick an Issue in `Ready` status whose prerequisites are all `Done`.
2. Create a branch named after the Issue number: `feature/ISSUE-<n>-<slug>`,
   `infrastructure/...`, `bugfix/...`, `security/...`, `docs/...`, `refactor/...`.
3. Make the change, write tests, verify in Docker (`make test`, `make lint`).
4. Update documentation (add an ADR if needed).
5. Commit messages must follow [Conventional Commits](https://www.conventionalcommits.org/):
   `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`.
6. Open a PR against `test`, referencing the Issue number (`Refs: #<n>`).
7. Merge once all CI checks are green. `test` → `main` only through the release process.

## Branch rules

| Branch | Rule |
|---|---|
| `main` | Only accepts PRs from `test`. Direct push/force-push/deletion forbidden. |
| `test` | Feature/infrastructure/bugfix/security/docs branches open PRs here. |
| `preview` | Only Renovate/Dependabot dependency PRs. |

## Commit and PR conventions

- Commit message: Conventional Commits, in English.
- **No AI co-author trailers, "Generated by" footers, agent-generation traces, or similar
  metadata** — see [CLAUDE.md](CLAUDE.md).
- Fill out the full PR template (Issue reference, Problem, Solution, Architectural impact,
  Database changes, API changes, Security considerations, Test evidence, Migration impact,
  Rollback strategy, Documentation updates, CI status).

## Local development

```bash
docker compose up -d
make test
make lint
```

No separate Python/Node/PostgreSQL/MongoDB/Redis/RabbitMQ installation on the host system —
Docker only. (Compose files are added in Phase 2.)
