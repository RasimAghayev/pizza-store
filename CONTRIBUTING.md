# Contributing

## Prinsip

Əvvəl infrastruktur, sonra biznes. Bax [README.md](README.md) və `docs/architecture/`.

## İş sistemi

Bütün işlər GitHub Issues üzərindən idarə olunur. Hər dəyişiklik bir Issue-ya bağlıdır.

1. `Ready` statusunda, bütün prerequisite-ləri `Done` olan Issue seç.
2. Issue nömrəsi ilə branch yarat: `feature/ISSUE-<n>-<slug>`, `infrastructure/...`,
   `bugfix/...`, `security/...`, `docs/...`, `refactor/...`.
3. Dəyişikliyi et, test yaz, Docker mühitində yoxla (`make test`, `make lint`).
4. Sənədləri yenilə (lazım olduqda ADR əlavə et).
5. Commit mesajları [Conventional Commits](https://www.conventionalcommits.org/) formatında
   olmalıdır: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`.
6. `test` branch-a PR aç, Issue nömrəsini PR-da qeyd et (`Refs: #<n>`).
7. Bütün CI yoxlamaları green olduqda merge edilir. `test` → `main` yalnız release prosesi ilə.

## Branch qaydaları

| Branch | Qayda |
|---|---|
| `main` | Yalnız `test`-dən PR. Birbaşa push/force-push/silmə qadağan. |
| `test` | Feature/infrastructure/bugfix/security/docs branch-ləri bura açılır. |
| `preview` | Yalnız Renovate/Dependabot dependency PR-ləri. |

## Commit və PR konvensiyası

- Commit mesajı: Conventional Commits, ingilis dilində.
- **AI co-author trailer, "Generated by", agent izi və oxşar metadata əlavə edilmir** — bax
  [CLAUDE.md](CLAUDE.md).
- PR şablonunu tam doldur (Issue reference, Problem, Solution, Architectural impact,
  Database changes, API changes, Security considerations, Test evidence, Migration impact,
  Rollback strategy, Documentation updates, CI status).

## Local development

```bash
docker compose up -d
make test
make lint
```

Docker. (Compose faylları Phase 2-də əlavə olunur.)
